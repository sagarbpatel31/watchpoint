# Watchpoint — Deployment Guide

Stack: **Supabase** (Postgres) → **Render** (FastAPI) → **Vercel** (Next.js)

All code is deployment-ready. No source changes required.

---

## Pre-flight checklist

- [ ] GitHub repo is public: https://github.com/sagarbpatel31/watchpoint
- [ ] Vercel CLI installed (`vercel --version`)
- [ ] Anthropic API key ready (optional — enables LLM summaries)

---

## Step 1 — Supabase (database)

**Time: ~5 min**

1. Go to https://supabase.com → **Start your project** → sign up
2. **New project**
   - Name: `watchpoint`
   - Database password: generate a strong one, save it
   - Region: **US West (North California)** — closest to Render Oregon
3. Wait ~2 min for provisioning
4. Go to **Settings → Database → Connection pooling** and select **Session mode**
5. Copy that URI — it looks like:
   ```
   postgresql://postgres.[PROJECT-REF]:[YOUR-PASSWORD]@aws-0-[REGION].pooler.supabase.co:5432/postgres
   ```
6. Save it — you'll paste this into Render as `DATABASE_URL`

> **Use the session pooler, not the direct connection.** The direct host
> (`db.[PROJECT-REF].supabase.co`) resolves **IPv6-only** on current Supabase
> projects, and Render's free tier has no IPv6 outbound. The container then dies
> at `alembic upgrade head` with a connection timeout *before uvicorn binds*, so
> you get a failed deploy with no application logs — the hardest kind to
> diagnose. The pooler host is IPv4 and still on port 5432.

> **Do not use transaction mode (port 6543).** Transaction pooling breaks
> asyncpg's prepared statements, which SQLAlchemy relies on throughout, and it
> makes the startup migration unreliable. Session mode is the one that works.

> The `normalize_postgres_url()` validator in `config.py` rewrites the scheme and
> strips `sslmode` automatically. Paste the URI exactly as Supabase gives it.

**Verify before continuing.** The host must resolve over IPv4, or Render cannot
reach it:

```bash
# Should print an A record (IPv4). If you only get AAAA, you copied the
# direct connection string rather than the session pooler.
dig +short A aws-0-[REGION].pooler.supabase.co
```

## Step 2 — Render (API backend)

**Time: ~8 min including build**

### 2a. Create account and connect repo

1. Go to https://render.com → **Get Started** → sign up with GitHub
2. **New → Blueprint**
3. Connect GitHub → select `sagarbpatel31/watchpoint`
4. Render will detect `apps/api/render.yaml` and propose one service: `watchpoint-api`
5. Click **Apply**

### 2b. Set environment variables

In the Blueprint env vars screen (before clicking Apply), set:

| Key | Value | Notes |
|-----|-------|-------|
| `DATABASE_URL` | `postgresql://postgres.[REF]:[PASSWORD]@aws-0-[REGION].pooler.supabase.co:5432/postgres` | The **session pooler** URI from Step 1 — not the direct `db.[REF].supabase.co` host |
| `ANTHROPIC_API_KEY` | `sk-ant-...` | Optional — get from console.anthropic.com |

These are the only two marked `sync: false`. Everything else is pre-configured in `render.yaml`:

| Key | Value (pre-set in render.yaml) |
|-----|-------------------------------|
| `CORS_ORIGINS` | `https://watchpoint-gray.vercel.app,http://localhost:3000,http://localhost:3001` — **check this against your real domain, see below** |
| `JWT_SECRET_KEY` | Auto-generated by Render |
| `STORAGE_PATH` | `/tmp/storage` |
| `PORT` | `8000` |
| `ENABLE_DEMO_SEED` | `false` — see Step 4 |

> **`CORS_ORIGINS` must match the domain Vercel actually serves.** The value in
> `render.yaml` is a default that was correct at some point; Vercel domains
> change when a project is renamed or re-linked. Read the production domain off
> the Vercel dashboard (Step 3) and set `CORS_ORIGINS` in the Render dashboard to
> match it exactly — scheme included, no trailing slash.
>
> Get this wrong and the symptom is misleading: the deployed frontend shows
> errors on every request and looks like the backend is down, while `curl`
> against the same API succeeds, because `curl` does not enforce CORS. If the API
> answers `curl` but not the browser, this is the cause.

> `JWT_SECRET_KEY` is generated once by Render. If you ever regenerate it, every
> token already issued stops working — don't touch it once anyone is using the
> deployment.

### 2c. Wait for build and get URL

The container runs `alembic upgrade head` before uvicorn binds. **Alembic owns the
schema** — the app no longer creates tables from model metadata at startup, so a
failed migration is a failed deploy rather than a silent divergence. Watch the
Render logs for the upgrade lines on first boot.

1. Build takes ~3–5 min (Docker build + pip install)
2. Once deployed, copy your service URL: `https://watchpoint-api.onrender.com`
   (may differ — use whatever Render assigns)
3. Verify it's live:
   ```bash
   curl https://watchpoint-api.onrender.com/api/v1/health
   # → {"status":"ok","service":"watchpoint-api","version":"0.1.0"}
   ```
   > First request may take ~30s if service just started.

**Verify before continuing.** In the Render logs for the first boot you should
see Alembic apply four migrations:

```
Running upgrade  -> 0001, Initial schema — all existing tables
Running upgrade 0001 -> 0002, Add AI layer tables: ...
Running upgrade 0002 -> 0003, Add device_tokens table ...
Running upgrade 0003 -> 0004, Align users.email and workspaces.slug indexes ...
```

If those lines are **absent** and the service never becomes healthy, the process
died before uvicorn bound — that is a database connectivity failure, not an
application bug. Go back to Step 1 and confirm you used the session pooler URI.

## Step 3 — Vercel (frontend)

**Time: ~3 min**

The frontend is already connected to Vercel and deploys automatically on every
push. You only need to set one env var and redeploy.

Substitute your real production domain for `<your-project>` everywhere below —
read it off the Vercel project page rather than assuming it, since it changes
when a project is renamed or re-linked.

```bash
cd apps/web

# Add the production API URL (replace with your actual Render URL)
vercel env add NEXT_PUBLIC_API_URL production
# When prompted, enter: https://watchpoint-api.onrender.com

# Redeploy to production with the new env var
vercel --prod
```

Alternatively via Vercel dashboard:
1. https://vercel.com → your `watchpoint` project → **Settings → Environment Variables**
2. Add: `NEXT_PUBLIC_API_URL` = `https://watchpoint-api.onrender.com` (scope: Production)
3. **Deployments → Redeploy** latest deployment

While you are in the dashboard, note the **production domain** at the top of the
project page. That exact string is what `CORS_ORIGINS` on Render must contain
(Step 2b). Set it now if it differs from the `render.yaml` default, and let
Render redeploy.

**Verify before continuing.** `curl` is not a sufficient check here — it ignores
CORS. Open the deployed frontend in a browser, load the dashboard, and confirm
data appears. If the page renders but every request fails while `curl` against
the same API succeeds, `CORS_ORIGINS` does not match this domain.

## Step 4 — Seed the production database

`POST /seed/demo` writes fixed-ID demo rows and takes no credentials, so it is
gated on `ENABLE_DEMO_SEED` and returns **404** when that is false. Leaving it
enabled would let anyone reset your public demo.

**Flip it on, seed, flip it back:**

```bash
# 1. Render dashboard → Environment → set ENABLE_DEMO_SEED=true → save
#    (this redeploys the service)

# 2. Seed
curl -X POST https://watchpoint-api.onrender.com/api/v1/seed/demo
# → {"status":"ok","seeded":{"users":1,"devices":3,"incidents":3, ...}}

# 3. Render dashboard → set ENABLE_DEMO_SEED=false → save
```

Seeding is idempotent — it deletes the previous demo rows (scoped strictly to
the fixed demo IDs) before inserting, so re-running replaces rather than
colliding on primary keys.

Demo credentials created by seed:
```
email:    demo@watchpoint.ai
password: demo123
```

## Step 4b — Provision a device token

Every ingest endpoint requires a device token in the `X-Device-Token` header.
Agents are headless, so they do not use the JWT flow. Tokens are stored as
SHA-256 hashes — the plaintext is shown **once**, at creation.

```bash
export API=https://watchpoint-api.onrender.com

# Log in as an operator to get a JWT
TOKEN=$(curl -s -X POST $API/api/v1/auth/login \
  -H "Content-Type: application/json" \
  -d '{"email":"demo@watchpoint.ai","password":"demo123"}' \
  | python3 -c "import sys,json; print(json.load(sys.stdin)['access_token'])")

# Register the device (operator action — agents can no longer self-register)
DEVICE_ID=$(curl -s -X POST $API/api/v1/devices/register \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"project_id":"<project-uuid>","device_name":"amr-07"}' \
  | python3 -c "import sys,json; print(json.load(sys.stdin)['id'])")

# Mint its token — copy token_once now, it is not retrievable again
curl -s -X POST $API/api/v1/devices/$DEVICE_ID/tokens \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"name":"amr-07 model collector"}' | python3 -m json.tool
```

A token may only write telemetry for the device it was issued to; a payload
naming any other device is rejected with 403. To revoke:

```bash
curl -X POST $API/api/v1/devices/tokens/<token-id>/revoke \
  -H "Authorization: Bearer $TOKEN"
```

Configure the agent with the token and the API URL — nothing else. The device it
reports as is resolved from the credential:

```bash
# Go edge agent
./edge-agent -api-url $API -token wp_...          # or export WP_DEVICE_TOKEN

# ROS 2 collector
python -m ros2_collector.main --api-url $API --token wp_...

# model-collector (in your inference process)
export WP_BACKEND_URL=$API WP_DEVICE_TOKEN=wp_...
```

> **Re-seeding revokes demo tokens.** `POST /seed/demo` deletes and recreates the
> demo devices, which cascades to their tokens. Mint a new one after any reseed.

> **The Go agent reports real measurements on Linux** — CPU from `/proc/stat`,
> memory from `/proc/meminfo`, disk from `statfs`, network from `/proc/net/dev`,
> and temperature from `/sys/class/thermal`. On any other OS it collects nothing
> and logs why, rather than substituting plausible-looking numbers.
>
> Two consequences worth knowing. The first tick reports no CPU or network
> figure: both are deltas between consecutive readings of counters that are
> cumulative since boot, so a single sample cannot produce them. And a reading
> the agent cannot take is omitted from the batch entirely rather than sent as
> zero — a device with no thermal sensors publishes no `cpu_temp_c` at all.

## Step 5 — Smoke test

Run these in order. All should pass.

```bash
export API=https://watchpoint-api.onrender.com

# 1. Health
curl $API/api/v1/health
# → {"status":"ok","service":"watchpoint-api","version":"0.1.0"}

# 2. Login
TOKEN=$(curl -s -X POST $API/api/v1/auth/login \
  -H "Content-Type: application/json" \
  -d '{"email":"demo@watchpoint.ai","password":"demo123"}' \
  | python3 -c "import sys,json; print(json.load(sys.stdin)['access_token'])")
echo "Token: ${TOKEN:0:20}..."

# 3. List incidents
curl -s $API/api/v1/incidents/ \
  -H "Authorization: Bearer $TOKEN" | python3 -m json.tool | grep '"title"'

# 4. Trigger analysis on first incident (get ID from step 3)
curl -s -X POST $API/api/v1/incidents/{INCIDENT_ID}/analyze \
  -H "Authorization: Bearer $TOKEN" | python3 -m json.tool | grep '"summary"'

# 5. Open frontend
open https://<your-project>.vercel.app
# Login with demo@watchpoint.ai / demo123
# Verify: dashboard loads, incidents show, analysis runs, replay bundle downloads
```

## Step 6 — Validate on real hardware (Raspberry Pi 5)

**Time: ~20 min. This is the only step that tests something a VM cannot.**

Every claim the edge agent makes about temperature is currently unverified on
hardware. The sandbox it was developed in exposes no thermal zones at all, so
`readThermalZones` has only ever been exercised against fixtures. A Pi 5 is
arm64 and has real thermal sensors, which makes it the cheapest way to find out
whether `cpu_temp_c` is real.

### 6a. Build and copy

```bash
# From the repo root. arm64 is already a CI target, so this should just work.
cd agents/edge-agent
GOOS=linux GOARCH=arm64 go build -o watchpoint-agent ./cmd/agent
scp watchpoint-agent pi@raspberrypi.local:~/
```

### 6b. Check the thermal zone label first

This is the step that actually matters. Before running the agent, look at what
the Pi calls its sensors:

```bash
# On the Pi
for z in /sys/class/thermal/thermal_zone*; do
  echo "$z: $(cat $z/type) = $(cat $z/temp)"
done
```

`classifyThermalZone` in `agents/edge-agent/internal/collector/proc.go` maps a
zone to `cpu_temp_c` if its label contains `cpu`, `x86_pkg_temp`, `coretemp`,
`acpitz` or `soc`, and to `gpu_temp_c` if it contains `gpu`. Pi OS normally
reports `cpu-thermal`, which contains `cpu` and therefore matches — **but that
is an assumption, and confirming it is the point of this step.**

If the label does not match any of those substrings, the zone is deliberately
ignored rather than guessed at, and no temperature is reported. Fix by adding
the label to `classifyThermalZone` and adding a row to `TestClassifyThermalZone`
in `proc_test.go` so it stays fixed.

### 6c. Run against the deployed API

```bash
# On the Pi. Mint the token per Step 4b.
export WP_DEVICE_TOKEN=wp_...
./watchpoint-agent -api-url https://watchpoint-api.onrender.com -interval 5s
```

The first tick reports `cpu=n/a` by design — CPU percent is a delta between two
readings of a counter that is cumulative since boot, so a single sample cannot
produce it. From the second tick you should see a line like:

```
Metrics sent (cpu=12.4%, mem=18.2% of 8052 MB, disk=24.1%, cpu_temp=47.8C)
```

If `cpu_temp` is missing from that line, 6b is where the answer is.

### 6d. Confirm the number tracks reality

A number appearing is not the test. A number *moving correctly* is.

```bash
# On the Pi, in another shell — cross-check the agent against the firmware
vcgencmd measure_temp
cat /sys/class/thermal/thermal_zone0/temp   # millidegrees; divide by 1000

# Now load all four cores and watch it climb
stress-ng --cpu 4 --timeout 120s      # or: for i in 1 2 3 4; do (while :; do :; done) & done
```

Expect idle around 45–55°C and a clear rise under load. The agent's reported
figure should track `vcgencmd measure_temp` within a degree. If the agent
reports a plausible but *static* temperature while `vcgencmd` moves, the reading
is being cached or misparsed.

### 6e. Sanity-check the rest on arm64

Worth a minute because these paths have only run on x86-64:

| Check | Compare against |
|---|---|
| `mem` percentage and total | `free -h` and `/proc/meminfo` `MemTotal` |
| `disk` percentage | `df -h /` — the agent matches `df`, using used/(used+available) |
| `cpu` percentage under load | `top` |

The disk figure is the one to look at hardest: `readDiskUsage` casts
`syscall.Statfs_t.Bsize`, whose width differs between 32- and 64-bit ARM. A
wildly wrong disk percentage would point there.

### 6f. Record the outcome

Update the temperature entry in `.ai/next_steps.md`, which currently states that
temperature is unvalidated on hardware. Either it is now validated, with the
zone label you found, or it needs the fix from 6b.

## Known limitations on free tier

| Limitation | Impact | Notes |
|-----------|--------|-------|
| Render cold start ~60s | First request after 15 min idle is slow | Add loading state on frontend |
| Supabase pauses after 1 week inactivity | ~30s resume lag | Resumes on first request automatically |
| `/tmp/storage` on Render is ephemeral | Replay bundles lost on restart/redeploy | Acceptable for demo; use S3 in production |
| Render free = 512MB RAM | Fine for this app | Watch if you add heavy ML inference |

## If something fails

**Render build fails:**
```bash
# Check build logs in Render dashboard → Events tab
# Common causes:
# - pip install failed (check pyproject.toml)
# - Dockerfile syntax error
# - Wrong rootDir in render.yaml (should be apps/api)
```

**API starts but DB errors:**
```bash
# Test DB connection
curl https://watchpoint-api.onrender.com/api/v1/health
# If 500 → Render logs → likely DATABASE_URL wrong or Supabase not ready

# Verify URL format — Render env var should look like:
# postgresql://postgres:PASSWORD@db.XXXXX.supabase.co:5432/postgres
# (config.py rewrites it to postgresql+asyncpg:// automatically)
```

**Frontend shows no data after login:**
```bash
# Most likely: NEXT_PUBLIC_API_URL not set or wrong
# Verify in Vercel: Settings → Environment Variables
# Then: Deployments → Redeploy (must redeploy after adding env var)
```

**CORS errors in browser console:**
```bash
# Update CORS_ORIGINS in Render env vars to include your exact Vercel URL
# No trailing slash: https://<your-project>.vercel.app NOT https://<your-project>.vercel.app/
# Redeploy Render service after changing
```

**Seed returns 500 (already seeded):**
```bash
# DB already has demo data — this is fine, use the existing credentials
# If you need a fresh seed, run in Supabase SQL editor:
# TRUNCATE users, workspaces, projects, devices, deployments, incidents,
#   event_logs, metric_points, incident_artifacts, annotations CASCADE;
# Then re-run the seed curl
```
